# Памятка для AI-ассистента (ежедневный обход обращений)

Этот файл — справочник для AI, который раз в день обходит обращения пользователей.

## Цель
Сократить мою личную нагрузку: AI самостоятельно проверяет фидбек, отвечает на простое,
правит безопасное, а спорное и потенциально опасное **кладёт в админский inbox**
(`/api/ai-proposals`, страница в CRM «🤖 AI-предложения») — я принимаю решение там.

## Доступ к данным
Прод-БД напрямую недоступна. Для разовой выгрузки / посева сообщений —
**временный** эндпоинт под `/api/diag/...` с секретом в query, через
`mcp__081f8cd7-...__web_fetch_vercel_url` (только GET). Сразу после
использования эндпоинт сносится отдельным коммитом. Деплой автоматический
по push в `claude/build-crm-system-JzCP9`.

## Что такое AI-предложение (ai_proposal)
Это запись в таблице `ai_proposals` с полями:
- `title` — короткая суть
- `summary` — подробно что хочу сделать (человеческим языком)
- `category` — `feature` / `bug` / `ui-tweak` / `business-logic` / другое
- `risk` — `low` / `medium` / `high`
- `source` — например `daily-run-2026-05-31` или `feedback-#17`
- `proposed_changes` — массив `[{file, action, reason}]`
- `feedback_id` — если связано с конкретным обращением
- `status` — `pending` → `approved`/`rejected`/`revision` → `done`

API:
- `POST /api/ai-proposals` — создать (нужно admin-роль)
- `GET /api/ai-proposals?status=approved` — забрать решения админа на следующем обходе
- `PATCH /api/ai-proposals/:id { decision: 'done' }` — отметить выполненным
- `GET /api/ai-proposals/pending-count` — счётчик для бейджа админу

## Категории фидбека и что с ними делать

### 1. УЖЕ СДЕЛАНО (узнать по коммитам / changelog за последние 24ч)
- Перевести связанное обращение в `awaiting_approval`, добавить admin_reply.
- Запостить в thread сообщение «Сделано, проверьте, нажмите ✅ Принимаю».
- Подпись: **«AI ассистент»** в `feedback_messages.user_name`.

### 2. БЕЗОПАСНАЯ ПРАВКА (можно делать автоматически)
Что считается безопасным:
- Текстовые правки: лейблы, плейсхолдеры, тексты подсказок, переводы.
- UI-тюнинги: цвета, отступы, размеры шрифта, иконки.
- Удаление поля как обязательного (если есть запасной флоу).
- Перестановка колонок в таблице по чёткой инструкции автора.
- Группировка/сортировка в списке если есть однозначный критерий.

**Что НЕ безопасно — создаём `ai_proposal` со `status=pending`** (не делаем сами):
- ❌ Деньги: касса, комиссии, цены, прайсы, выручка.
- ❌ Удаление данных любого рода (даже «очистка тестовых»).
- ❌ Резервы / синхронизация с МойСклад (если не разобран кейс).
- ❌ Права доступа, авторизация, пароли, токены.
- ❌ Архитектурные изменения, новые таблицы, новые сущности.
- ❌ Изменение бизнес-логики (статусы заказа, переходы, валидации).

### 3. ТРЕБУЕТ УТОЧНЕНИЯ ОТ АВТОРА (не от админа)
Если суть запроса понятна не до конца — задаём 2-4 вопроса автору, на простом языке,
в thread обращения через `feedback_messages`. Подпись «AI ассистент».

**ВАЖНО:** уточнение задаётся только ОДИН РАЗ. Если автор не ответил —
**больше не пиши**. Не дёргай новыми вопросами, не переформулируй, не напоминай.
Молча оставь обращение в `open` (или переведи в `closed` если очевидно
дубль/неактуально). Повторные вопросы — это спам в инбоксе автора.

Алгоритм: смотри `feedback_messages` для этого обращения. Если последнее
сообщение от AI — НЕ ПИСАТЬ. Если последнее от автора и без ответа — можно
ответить (один раз).

### 4. ДУБЛИКАТЫ / СПАМ / ТЕСТЫ
- Закрыть статусом `closed` с короткой пометкой.
- Не задавать вопросов. Подпись «AI ассистент».

## Цикл работы с ai_proposals (входящий inbox от прошлых обходов)

В начале каждого обхода:
1. `GET /api/ai-proposals?status=approved` — что админ принял. Для каждого:
   - **Прочитать тред:** `GET /api/ai-proposals/:id/messages`. Все
     сообщения админа после твоего последнего ответа — это уточнения
     к задаче, обязательно учесть при реализации.
   - Сделать коммит, deploy.
   - `PATCH /:id { decision: 'done' }`.
   - Если был связан с feedback — перевести в awaiting_approval.

2. `GET /api/ai-proposals?status=revision` — что админ просит переработать.
   - Прочитать `admin_notes` (финальная заметка решения) **И** тред
     `/messages` (все накопившиеся уточнения).
   - Переработать предложение, обновить summary через `PATCH` или создать
     новое `POST`, статус снова `pending`.
   - Опционально: ответить в тред `POST /messages` с пометкой «учёл X, Y».

3. `GET /api/ai-proposals?status=rejected` — что админ отклонил.
   Если связано с feedback — закрыть обращение с пометкой «не подходит» от AI.

4. **Pending-предложения с новыми сообщениями от админа.** Раз в обход
   пройти `GET /api/ai-proposals?status=pending`, для каждого глянуть
   `/messages` — если есть сообщения от админа после твоего последнего
   (или вообще без твоих ответов) → ответить в тред. Тред нужен именно
   для итеративного уточнения до принятия решения.

**Тред заметок (`ai_proposal_messages`) — обязательная часть контекста.**
Не имея доступа к нему, AI пропустит замечания админа, которые тот
оставил между обходами. `admin_notes` — только финальная заметка при
смене статуса; всё промежуточное обсуждение живёт в треде.

POST в тред: `POST /api/ai-proposals/:id/messages { text, user_name: 'AI ассистент' }`.

## Формат ответов AI

### В thread обращения (`feedback_messages`)
- Здороваемся.
- Кратко повторяем что просил автор (показываем что прочли).
- Чёткие пронумерованные вопросы / список сделанного.
- Если просим попробовать — приписываем «Ctrl+F5 для сброса кеша».
- `user_name` = **«AI ассистент»**, `role` = `admin`.

### В ai_proposal (для админа)
- `title`: «Что-то конкретное. Например: добавить колонку XYZ в список заказов»
- `summary`: что хочу, зачем, как пользователь это увидит, риски, оценка времени
- `proposed_changes`: список файлов и действий
- `risk`: оцениваю честно (high если деньги/удаления/архитектура)

## Безопасность бэкенда
- Не пушить с дефолтным `JWT_SECRET`.
- Не трогать `касса/cashbox`, `payments` (деньги) без явного запроса.
- Никаких destructive операций без подтверждения через ai_proposal.
- Все DDL — идемпотентные, через `ensureInitialized()` и SCHEMA_VERSION-бамп.
- Деплой только через прод-ветку `claude/build-crm-system-JzCP9`.
  Dev-ветка задаётся в session-specific задании (меняется каждую сессию) и
  **обычно оказывается orphan-веткой без общего предка с прод-веткой**
  (`fatal: refusing to merge unrelated histories`) — это норма для этой среды,
  не баг, не пытаться чинить рёбейзом/force-push. `git merge --ff-only` в
  таком случае гарантированно упадёт — **не трать на него больше одной
  попытки**, сразу переходи к cherry-pick.
  Порядок: `git checkout claude/build-crm-system-JzCP9` →
  **`git fetch origin claude/build-crm-system-JzCP9`** (обязательно! прод может
  быть force-pushed другой сессией) → `git reset --hard origin/claude/build-crm-system-JzCP9`
  (если локальная отстала) → попробовать `git merge --ff-only <dev-ветка>`,
  при unrelated-histories сразу `git cherry-pick <commit(ы) с реальными
  изменениями>` по одному прямо в прод-ветку → push.
  (См. ai_proposal #54 от 2026-06-19 — тот же диагноз, помечено done, но
  проблема продолжала возвращаться минимум до 2026-07-02, т.к. эта заметка
  была недостаточно явной. Если увидишь очередной цикл failed-ff-merge
  через несколько дней после этой правки — предложение не прижилось, эскалируй
  пользователю вместо очередной попытки почитать этот файл ещё раз.)

  **2026-07-07 (v169), находка про shallow-clone и удалённую dev-ветку:**
  сессия стартовала с shallow-клоном (`git rev-parse --is-shallow-repository`
  = true, глубина ~50 коммитов). На таком клоне `git merge-base`/`git log
  A..B` между dev и prod могут ЛОЖНО показывать «unrelated histories» или
  пустой список коммитов — это артефакт обрезанной истории, а не реальное
  расхождение. **Перед тем как делать вывод о unrelated-histories или
  force-push — сначала `git fetch --unshallow origin`** (быстро, ~10-20с),

  была dev-ветка. Восстановил по правилу «PR уже смержен» из системных

  прод → снос). Если в будущем обходе снова `git ls-remote` не находит
  designated dev-ветку — это, видимо, штатное поведение среды после
  смержа (не баг), чинить тем же способом.

## Граблина: `git add file1 file2` при снятии diag-эндпоинта

**2026-07-08 (v210), найдено при снятии diag-эндпоинта:** шаг «снести diag
одним коммитом» обычно делается так: `git rm -f src/routes/diagDaily.js`,
затем Edit убирает импорт/роут из `app.js`, затем `git add src/app.js
src/routes/diagDaily.js && git commit`. **Опасность:** если `git rm`
уже убрал файл из рабочего дерева, второй pathspec в `git add` (сам
удалённый файл) не существует — `git add` падает с `fatal: pathspec
'...' did not match any files` и **не стейджит вообще ничего из
команды**, включая `src/app.js`, если это была одна команда с `&&`.
При этом `git rm` заранее застейджил удаление файла — коммит всё равно
проходит (молча, без ошибки на самом commit), но содержит только
удаление файла, **без правки `app.js`** — импорт/роут на уже
несуществующий модуль остаётся в коде. Дальнейший `git reset --hard`
(шаг синхронизации prod-ветки) стирает несохранённые правки `app.js`
из рабочего дерева безвозвратно, и в prod чуть не улетел коммит,
ломающий холодный старт (import несуществующего файла крашит
приложение). Поймано и исправлено ДО пуша в prod-ветку — но ветка dev
(`origin/claude/inspiring-cannon-v8c47w`) на несколько секунд уже
содержала битый коммит `88bc71b`, закрыто следующим коммитом `a377df7`.

**Как избежать:** стейджить `app.js` и удаление diag-файла **раздельно**
(`git add src/app.js` отдельной командой, `git rm` — отдельной, без
`&&`-цепочки одной командой с несуществующим путём), либо просто
`git add -A -- src/app.js src/routes/` перед коммитом. После коммита
на снос diag — **обязательно** `git show <commit> --stat` и `grep -n
diag src/app.js` перед пушем, чтобы убедиться, что `app.js` реально
попал в тот же коммит, что и удаление файла.

## Аварийные ситуации — СТОП, не выкручиваться

Если что-то из ниже происходит — **немедленно остановиться**, создать ai_proposal
с описанием проблемы и закончить обход. НЕ пытаться обойти своими силами:

- `git push` падает с auth/signing ошибкой → среда настроена неправильно, не лезь в токены.
- `git commit` валится на pre-commit/signing → НЕ использовать `--no-verify` / `--no-gpg-sign`.
- API возвращает 401/403 → не искать токены в логах, env, других проектах.
- Не находишь репо/файлы → сессия стартовала без source, не пытайся клонить вручную.
- Supabase MCP, Vercel logs/tokens, OAuth-секреты — **никогда не лезть** в поисках доступов
  к прод-БД, токенов, чужих проектов. Прод-БД крутится внешним сервисом, доступа к ней
  у тебя нет и не должно быть.
- Любая операция требует >5 попыток подряд — стоп, эскалируй через ai_proposal.

В таких случаях:
1. `POST /api/ai-proposals` с `risk: 'high'`, `category: 'infra'`,
   `title: 'Schedule не может пушить / читать репо'`,
   `summary: <что именно сломано, как воспроизвести>`.
2. Завершить обход коротким отчётом «не смог из-за инфры».
